## plan-auditor — round 1

I verified the plan's repo claims directly against `upstream/master` (`2.0.49`), the fork `HEAD`,
and a simulated install of the post-reset + post-bump dependency tree. Most of the plan's grounding
is accurate: upstream's constructor is exactly the 10-positional signature ending at `refreshToken`,
the `eval(prefix + 'refreshToken')` field assignment and `_.isObject(consumerKey)` dual construction
are present, upstream's `refreshAccessToken` is axios-based with `function(res){…}.bind(this)` `.then`
/ `.catch` and no hook (the Phase 2 example shape matches the real upstream handler), `index.d.ts`
exists upstream with the 10-param constructor at lines 464-475, `"types": "index.d.ts"` is set, the
`tokenSecret` guard is skipped for `oauthversion '2.0'` (so the test's `makeClient` reaches the
refresh path), `Promise` is upstream's bound `bluebird`, the d.ts grep-gate string matches, and the
module loads cleanly against `fast-xml-parser@5.9.2`. Those checks pass and are not re-raised below.

One blocking factual error propagates from the design into Phase 4's audit gate, plus a few smaller
gaps.

## Findings

| ID | Severity | Status | Category | Finding | Recommendation / update |
|----|----------|--------|----------|---------|-------------------------|
| plan-auditor-r1-f1 | Blocker | Open | Assumption | Phase 4's audit gate is non-executable as written. The plan (Step 3, exit gate) asserts that **no advisory whose module is `uuid` remains** and treats `uuid` as "removed with request." Verified against a simulated install of the exact post-reset + post-bump tree: upstream `2.0.49` re-declares `uuid@^8.3.2` as a **direct** dependency (used at upstream `index.js:2352`, `uuid.v1()`), so the reset does **not** remove it. `npm audit` on that tree reports `uuid <11.1.1` — `GHSA-w5hq-g745-h8pq` (moderate) — as the one remaining vulnerability. The gate as specified will fail. (Same applies to the design's Success-Criteria table, which mis-attributes `uuid` and `form-data` to "via request"; `form-data@^4.0.5` happens to resolve clean at 4.0.6, but `uuid` does not.) | Decide and encode one of: (a) add a third bump `uuid` to a fixed line (`>=11.1.1`) in Phase 4 Step 1 — note this is a semver-major from 8.x and the plan must then verify `uuid.v1()` still resolves under the new major; or (b) consciously re-scope the gate to accept the residual moderate `uuid` advisory, which contradicts the design's "all eight cleared / clean audit" success criterion and therefore needs design-owner/human disposition. Either way, fix Phase 4's claim that `uuid` is "removed with request," and correct the eight-advisory enumeration so the gate is truthful and falsifiable. |
| plan-auditor-r1-f2 | High | Open | Consistency | Phase 4 Step 3 / exit gate uses a substring grep over `npm audit --json` (`grep -q "\"$m\""`) to assert each named module is absent. This is unsound for `uuid`/`form-data`/`underscore`/`fast-xml-parser`: those package names appear in `npm audit --json` output as dependency-path keys and `via` references **even when not the flagged advisory**, and conversely a clean module simply won't appear — so the loop both false-positives and gives no signal on the actual advisory IDs. The design itself (Verification) calls for asserting "each of the eight named advisories is absent," not a name-substring scan. | Replace the substring scan with a check against `.vulnerabilities` keys (e.g. `npm audit --json | jq '.vulnerabilities | keys'` must be empty of the named modules) or assert `.metadata.vulnerabilities` totals are zero for the relevant severities. Make the gate key on advisory presence, not raw name occurrence in the JSON. |
| plan-auditor-r1-f3 | Medium | Open | Test | The rejection-isolation test (Phase 3 case 4) asserts only `callbackArgs[0] === null` and the success payload inside a single `setImmediate`. It does **not** actually prove the rejection was contained by the hook's *own* `.catch` rather than escaping as an unhandled rejection — the design's Success Criteria explicitly require pinning that structure ("captured by the hook's own `.catch` … not merely that nothing threw"). The plan even flags the `process.on('unhandledRejection', …)` capture as "optional," leaving the strongest assertion unenforced; and a single `setImmediate` may resolve before the hook's microtask-chained `.catch` settles, making `hookSettled` unobserved. | Make the unhandled-rejection capture **mandatory**, not optional: register `process.on('unhandledRejection', …)` (or `once`) in the test and assert it never fires for the hook rejection, and assert `hookSettled === true`. Sequence the final assertions after the hook's promise chain has settled (e.g. chain off the stub/hook promise, or use a short `setTimeout`/awaited tick) rather than relying on one `setImmediate`. |
| plan-auditor-r1-f4 | Medium | Open | MissingDecision | Phase 1 Step 4 and the Phase 2 exit gate defer the `node -e "require('./index.js')"` module-load smoke test to "Phase 4 once npm install has run," but **no `npm install` runs before Phase 4** — the reset brings in upstream's `package-lock.json` but never installs `node_modules`. So Phases 1-3 author and gate `index.js`/`index.d.ts`/the test with **no installed dependencies**, and the Phase 3 exit gate (`npx mocha test/refreshTokenCallBack.test.js`, which `require`s `axios` and `../index`) cannot run — `require('axios')` will throw `MODULE_NOT_FOUND`. The plan never states when deps first become available. | Add an explicit `npm install` (or `npm ci`) step at the **start of Phase 3** (or end of Phase 1) so the Phase 3 regression-test gate is actually runnable; Phase 4's clean-regen `rm -rf node_modules package-lock.json && npm install` then re-resolves with the bumps. State the dependency-availability point explicitly so no phase gate is silently unrunnable. |
| plan-auditor-r1-f5 | Low | Open | Consistency | Phase 1 Step 4 / exit gate greps `grep -q '"types": "index.d.ts"' package.json` and the precondition greps `grep "_.isObject(consumerKey)"` and `grep -c "request.post("`. Verified the strings match upstream, **but** several gate greps embed unescaped `.` and `(` as regex metacharacters (`request.post(`, `_.isObject(consumerKey)`); they happen to match here only because the literal text also satisfies the regex. This is fragile (e.g. `request.post(` would also match `requestXpostY`) and the count-based gates (`grep -c … returns 0`) invert shell exit status, which can mislead an implementor scripting `&&` chains (a `grep -c` returning `0` exits non-zero). | Use `grep -F` (fixed-string) for the literal assertions, or anchor/escape the metacharacters; and for count gates capture the numeric output explicitly (`[ "$(grep -c … )" = 0 ]`) rather than relying on `grep`'s exit code. |
