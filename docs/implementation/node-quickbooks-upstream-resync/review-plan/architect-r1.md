## architect — round 1

Plan Review Mode. I reviewed `docs/implementation/node-quickbooks-upstream-resync/plan.md` against its
design doc, along the five plan axes (module boundaries & dependency direction; data model & schema;
public API surface; migration / phase sequencing; performance & hot paths). I verified the load-bearing
upstream/fork facts directly against `upstream/master` (`2.0.49`) and `HEAD`:

- Upstream `refreshAccessToken` is axios-based, sets `this.refreshToken`/`this.token` unconditionally in
  `.then`, no hook, no rotation guard — confirmed (upstream `index.js:135-142`).
- Upstream constructor is 10 positional params ending at `refreshToken`; `_.isObject(consumerKey)` dual
  construction present; `index.d.ts` constructor ends at `refreshToken?: string | null` — confirmed.
- `Promise = require('bluebird')` is bound at top of upstream `index.js:16` — confirmed (the plan's
  `Promise.resolve(...)` note is valid).
- `mocha@10.1.0`, `"test": "mocha"`, no `.mocharc`, `test/{batch,cdc,charge,index}.js` live suites —
  confirmed (the isolated-run gate concern is real).

The plan is unusually thorough and most decisions are sound and well-justified. The findings below are
the gaps that remain. The most material is a genuine behavioral divergence the plan's "identical
observable behavior" framing does not surface (f1): the fork's pre-reset success/failure branching is
**HTTP-body-based** (`invalid_grant` detection on `r.body`), whereas upstream's axios path is
**HTTP-status-based** (`.then` vs `.catch`). The reset changes the error-classification contract on the
non-rotation/failure paths, which the plan treats as out of scope without saying so.

## Findings

| ID | Severity | Status | Category | Location | Finding | Recommendation / update |
|----|----------|--------|----------|----------|---------|-------------------------|
| architect-r1-f1 | Medium | Open | PublicAPI | Phase 2 / Decision 3; plan.md:113-152 | The plan frames Phase 2 as preserving "observably identical" callback behavior, but it only preserves the **success/rotation/hook** semantics. The fork's pre-reset success detection is HTTP-**body**-based: `if (r && r.body && !(r.body.error === 'invalid_grant'))` routes to the success branch and calls `callback(e, refreshResponse)` with `e` (request's transport error, normally `null`); the `else` branch calls `callback(e, r, data)`. Upstream's axios path is HTTP-**status**-based: any non-2xx (incl. a 400 `invalid_grant`) goes to `.catch` → `callback(err, err.response, …)`. So after the reset the *failure* callback shape and the boundary between success/failure change for `fuze`'s coordinator. The plan never states this divergence is accepted — it reads as if the whole callback contract is preserved when only the success half is. | Add an explicit note (Phase 2 Notes or Assumptions) that the reset intentionally adopts upstream's HTTP-status-based success/failure classification and `.catch` error-callback shape, replacing the fork's body-based `invalid_grant` detection. Confirm `fuze`'s shim/coordinator only observes the success path (the rotation hook) and is indifferent to the error-arg shape, or list this as a Deferred-Validation item to check against `fuze`'s token-refresh tests. Without this the "identical observable behavior" claim is overstated. |
| architect-r1-f2 | Low | Open | PublicAPI | Phase 3 / plan.md:204, 219-301 | `index.d.ts` types the hook param as `(token: string) => void | Promise<void>` (one positional `token` arg), but neither the runtime re-apply nor the test pins the hook's **call arity**. The runtime calls `this.refreshTokenCallBack(this.refreshToken)` — one arg — matching the type, but the plan never asserts the call site passes exactly that. If an implementor passed `(token, refreshResponse)` the type and runtime would silently diverge and `fuze` (which casts) wouldn't catch it. | Add a gate or test assertion that the hook is invoked with exactly the rotated token as its single argument (e.g. assert `seen === 'NEW'` already does the value; additionally assert the hook received one argument), so the `.d.ts` signature and runtime stay locked together. |
| architect-r1-f3 | Low | Open | Migration | Phase 1 Step 2 / plan.md:69 | The "no third reconciliation point" precondition is asserted via `git diff upstream/master:index.js HEAD:index.js` with a human "shows no third feature region" read — but the gate is not falsifiable/mechanical. Every other precondition in Phase 1 is a `grep -qF` / captured-count check; this one relies on eyeballing a large request↔axios rewrite diff. A real third delta could hide in that noise. | Either drop the claim to "best-effort manual confirmation (not a hard gate)" explicitly, or make it mechanical: diff only the two known regions (constructor line, `refreshAccessToken` body) and assert the rest of the fork's non-rewrite, feature-bearing tokens (`refreshTokenCallBack`, the rotation guard) account for the entire fork-only addition set. As written it is presented as a gate but isn't one. |
| architect-r1-f4 | Low | Open | Migration | Phase 3 Step 3 / plan.md:186-188 | The plan correctly runs the new test in isolation (`npx mocha test/<file>`) because `npm test` would also run the credentialed live suites. But it leaves `npm test` itself in a state where it fails without credentials — meaning the package's advertised `scripts.test` is red in any unattended/CI context after this work, and a future maintainer (or `fuze` CI) running `npm test` gets a failure unrelated to the feature. The plan defers this as "upstream verbatim" but inherits a known-broken-offline test script as the package's only `test` entrypoint. | State explicitly (Assumptions or Deferred Validation) that `npm test` remains credential-gated and the regression gate is the isolated invocation; OR add a follow-up note that the offline regression test is the de-facto CI gate so a future maintainer doesn't assume `npm test` green is required. A `Defer:` to add a `.mocharc`/`test:unit` script split is acceptable but should be named, not silently left broken. |
| architect-r1-f5 | Low | Open | DataModel | Phase 4 / plan.md:327, 377 | The `uuid` bump uses `">=11.1.1"` (an unbounded lower-bound range), unlike the other two bumps which use caret pins (`^1.13.8`, `^5.9.2`). An open-ended `>=` floats across **all future majors** (12, 13, 14, …) with no upper bound, so a future `npm install` could silently pull `uuid@15+` with an unverified API for the `uuid.v1()` call site — the plan verified only `14.0.0`. This is inconsistent with the design's "thin patch layer / pinned, well-understood" posture. | Pin `uuid` consistently with the other two bumps, e.g. `^14.0.0` (caret on the verified current major) or `^11.1.1`, bounding it within a tested major rather than `>=`. The advisory is cleared at `>=11.1.1` either way; the caret keeps the float within a single major as the plan does for `fast-xml-parser`. |
| architect-r1-f6 | Low | Open | Migration | Phase 3 Step 0 vs Phase 4 / plan.md:177-179, 328 | Phase 3 installs `node_modules` over the inherited lock (`fast-xml-parser@4.x`), runs the test and a module-load smoke test against 4.x; Phase 4 then `rm -rf`s and reinstalls against 5.x and re-runs. The Phase 3 install/verify against the soon-to-be-discarded 4.x tree is wasted work whose only value is proving the *feature code* loads independent of the bumps — but that value is real (isolates feature bugs from bump bugs). The plan doesn't state this is the rationale, so it reads as redundant install churn. | Add one sentence in Phase 3 Step 0 noting the 4.x install is deliberate sequencing (prove the re-applied feature loads/passes *before* layering the dependency bumps, so a Phase 4 failure localizes to the bump). One line; otherwise a reviewer will flag it as removable. |
