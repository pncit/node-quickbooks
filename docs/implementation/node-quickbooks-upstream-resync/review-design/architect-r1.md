## architect — round 1

Design Review Mode. Reviewed against the design's stated Problem / Goals / Non-Goals as the scope
boundary. The design is well-scoped, decisive, and largely tight: the fork's identity ("upstream +
one feature + two bumps") is a sound architectural framing, the boundary surfaces are correctly
identified (two regions of `index.js`, plus the newly-inherited `index.d.ts`), and the dependency
direction is unchanged (fork stays the consumed artifact; `fuze` stays the consumer). Most decisions
need no further work.

I verified the load-bearing claims against source: `index.js:103` (11-param positional ctor + object
form via `eval` prefix), `index.js:118` (`this.refreshTokenCallBack` populated), `index.js:147–162`
(`request.post` with `async` node-style callback; `await` on `155` inside the rotation guard at
`152`), and the auto-memory consumer contract. The findings below concern internal consistency and a
plannability gap in the error-semantics decision — the one place where "identical observable
behavior" is asserted but the actual current behavior is more subtle than the design states.

### Findings

| ID | Severity | Status | Category | Location | Finding | Recommendation / update |

| architect-r1-f1 | High | Open | Architecture | Decision 3 (l.157–169); Migration step 2 (l.216) | The design names the contract to preserve ("hook rejection not routed into node-style callback") but does not specify the *mechanism* that produces it today, so step 2 is under-specified and the implementor can satisfy the prose while breaking the contract. The current behavior is not "we deliberately don't await" — the code *does* `await this.refreshTokenCallBack(...)` (`index.js:155`), but inside an `async` callback passed to `request.post` whose returned promise is **discarded**; a rejection therefore becomes an *unhandled rejection*, never reaching `callback`. On axios (`.then().catch(callback)`), an `await`ed hook rejection inside the same `.then` flows straight into `.catch → callback(err)` — the opposite behavior — even though the code "looks" identical. The decision must state the concrete re-apply shape: invoke the hook such that its rejection cannot enter the `.then`/`.catch` chain feeding `callback` (e.g. fire without `await` in the chain, or isolate it), and call out that a naive `await` in the axios `.then` is the specific wrong answer. | In Decision 3, add a sentence pinning the mechanism: today the hook is `await`ed inside a node-style callback whose promise `request` discards (rejection → unhandled rejection, never reaches `callback`); the axios re-apply must reproduce *that* (rejection isolated from the `.then`/`.catch → callback` chain), and must NOT `await` the hook inside the `.then` that resolves the caller's `callback`. |
| architect-r1-f2 | Medium | Open | Architecture | Non-Goals (l.49); Decision 3 rationale (l.166–168); l.99 | Internal inconsistency in how the current contract is characterized. The consumer-quote (l.98–99) says "node-quickbooks does NOT await this callback," but the fork source `await`s it (`index.js:155`) and Decision 3 reasons about "`await this.refreshTokenCallBack(...)` inside the same `.then()`." Left unreconciled, the implementor cannot tell whether the target is "don't await at all" or "await but isolate." Since f1 resolves the mechanism, this finding asks the design to explicitly note that `fuze`'s comment describes the *observable* effect (effectively fire-and-forget to the caller), not the literal absence of `await`, so the two statements stop appearing to contradict. | Add a half-sentence in Current State or Decision 3 reconciling the two: the fork *does* `await` the hook, but because the awaiting function's promise is discarded by `request`, the caller observes fire-and-forget — which is the property to preserve. |
| architect-r1-f3 | Medium | Open | Architecture | Decision 1 / Migration step 1 (l.214–215); l.55 | The design asserts reconciliation is confined to "exactly two places — `package.json` and `index.js`" and "everywhere else, upstream wins," but the fork's `index.js` carries at least one production divergence the design does not enumerate as a reconciliation point: the fork pins `minorversion` default to `75` (`index.js:115`), whereas the design's net-delta claim is "exactly this one feature." If upstream's default differs, "upstream wins" silently changes request behavior for `fuze`. The design should either confirm (in the Precondition) that no non-feature production deltas exist between fork and upstream `index.js`, or list them so the merge doesn't drop/alter them unnoticed. | In Migration step 0 (Precondition), add: diff fork `index.js` against upstream `2.0.50` `index.js` and confirm the *only* production deltas are the two feature regions; if any other delta exists (e.g. `minorversion` default), enumerate it as an explicit reconciliation decision rather than letting "upstream wins" silently apply. |
| architect-r1-f4 | Medium | Open | PublicAPI | Decision 2 (l.144–145); Breaking Changes (l.224–228) | The `index.d.ts` constructor type is specified only for the *positional* form, but the runtime constructor also supports the **object form** (`_.isObject(consumerKey)` prefix trick, `index.js:104`). The design declares "the package's public constructor shape (positional **and** object forms)" stays the same (l.282), yet Decision 2 types only 11 positional params. If upstream's inherited `index.d.ts` already omits the object overload, the design is consistent only because `fuze` uses the positional form; but the design should state that the object form is intentionally left untyped (and why that's safe for the consumer) rather than leaving a silent gap between the "what stays the same" claim and the typed surface. | In Decision 2, note that only the positional form is typed (matching upstream and `fuze`'s usage); the object-form constructor remains untyped by design, and that is acceptable because `fuze` constructs positionally. If upstream already types an overload, state that it is preserved. |
| architect-r1-f5 | Low | Open | Architecture | Decision 4 (l.188–190); Risks table (l.293) | The `fast-xml-parser` 5.x "no breaking change for this codebase" rationale rests on the call site being `new XMLParser()` with default options — but the fork instantiates the parser at *module load* as a top-level singleton (`index.js:17`, `xmlParser = new (require('fast-xml-parser').XMLParser)()`), not per-call. The design's stated call site (`new XMLParser().parse(body)[rootTag]`, l.52, l.188) does not match the actual singleton instantiation. This is minor but means the design's verification anchor ("the fork's only usage is …") is slightly wrong; an implementor checking the 5.x default-options behavior should verify the *singleton-at-require* pattern (5.x must not change constructor defaults or throw at construction with zero args), which the design's phrasing obscures. | Correct the stated call-site description to match `index.js:17` (module-load singleton `new XMLParser()` with no options, reused via `xmlParser.parse(...)`), and have Verification confirm 5.x's zero-arg constructor + default `parse` output are unchanged. |
| architect-r1-f6 | Low | Open | Migration | Success Criteria / Verification (l.264–276) | Verification relies on a `fuze` checkout to confirm the type-check/build (l.273) and on optional sandbox creds for live API (l.276), but the regression test that "locks the contract" (a core Goal, l.41) is specified only as stubbing `axios.post`. The design does not state where the hook is invoked relative to the discarded-promise mechanism (f1), so the test as described ("callback fired once with success result and no error when the hook rejects") can pass even if the implementor isolated the rejection by accident in a way that diverges from upstream's structure. This is a plannability nit: tie the test assertion explicitly to the mechanism from f1 so the test is testing the contract, not just the symptom. | Once f1 fixes the mechanism, add to the test spec: assert the hook rejection surfaces as an unhandled-rejection-equivalent (or is explicitly caught by the re-apply), distinct from the node-style `callback`, so the test pins the *structure* and not only the observable "callback fired with no error." |
